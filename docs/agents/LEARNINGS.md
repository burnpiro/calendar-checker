# Durable notes for future agents

Keep concise, verified implementation facts here. Include the date and supporting source/test when it helps. Store no credentials, personal account information, raw API responses, or speculative findings. Move major design choices into an ADR.

## 2026-11-01

- This project began as an empty folder. The user requested local Git and documentation; no remote or publishing is authorized by that request.
- The unpacked extension ID is fixed by `config/extension-key.json`. `npm run extension:id` prints it. The public key can be committed; a private signing key must not be.
- The user configured an OAuth client in the ignored local environment file. Never overwrite it or replace it with a synthetic test value in a final build. Full real OAuth validation remains pending until the validation matrix is exercised.
- Account identity is Google's verified `sub`. Pin known-account token requests to it and compare returned identity before calendar access.
- Native account chooser behavior remains unverified with actual accounts. Do not infer success from injected adapter tests.
- Stage 1's timing preference schedules authentication/calendar-list checks, not event synchronization. Full custom notification sounds and event-sync settings remain in the plan.
- In restricted coding environments, npm registry access and launching Chromium may need sandbox escalation. The successful browser tests used a temporary profile and `PLAYWRIGHT_BROWSERS_PATH=/private/tmp/calendar-checker-browsers`; personal Chrome data was never used.
- Account toggle state is controlled by the persisted worker response. Browser tests should click and await the final checked state instead of assuming synchronous checkbox updates.
- WXT manifest environment values must be read in the manifest callback, after dotenv loading. See `wxt.config.ts` and WXT environment-variable documentation.
- Avoid shell variable names such as `path` in zsh: `path` is tied to `PATH` and can accidentally hide installed tooling. Use task-specific variable names.
- A generic connection error after consent was traced to calling stored native `fetch` as `this.fetcher(...)`. Chrome requires the Window/Worker global receiver and threw `Illegal invocation` before any request. Direct probes worked, while injected Node mocks missed this. The default transport now wraps `globalThis.fetch`; preserve this wrapper and its real-worker test.
- Transport diagnostics use fixed safe stages/categories plus HTTP status or a bounded native numeric code. Never retain full Chrome/provider error strings. GET retries are bounded to two attempts, and partial-body timeouts are transport failures rather than malformed JSON.
- After the native-fetch fix was rebuilt/reloaded, the user confirmed successful account connection on 2026-11-01. This verifies the first account flow; multi-account and lifecycle acceptance are still pending.
- Stage 2 uses FullCalendar v7's native React package, with daygrid/timegrid/interaction and Forma theme bundled. V6 examples and hashed internal CSS selectors are unsuitable. Use installed types and public class hooks/theme variables. Override theme variables on the calendar's `data-color-scheme` root for consistent dark mode.
- FullCalendar's day-cell event container uses measured inline `min-height` for its absolutely positioned events. Do not force that container to zero: overflow controls will overlap events. The compact popup instead reduces date/event text sizes and row minimum height through public hooks. The Chromium test verifies all six rows and overflow geometry.
- Historical stage 2: `calendar-checker-events` schema 1 separates `events`, `demoEvents`, and `meta`. Only worker commands write samples; reset clears sample rows and `demo-v1:` markers. Google sync has no writer yet. Superseded by schema 3 removal of preview data.
- Old stage 1 preferences receive additive appearance defaults. Commands use strict partial patches with per-key calendar visibility merging. Full preference objects must not enter diagnostics: visibility keys contain account/calendar IDs.
- Timed event ordering compares actual Temporal instants, including fractional seconds. All-day ends stay exclusive and date-only. The tests exercise Warsaw's March 2026 DST change and overnight date labels.
- Stage 2 passes 67 unit/adapter tests and three isolated Chromium tests. Run `npm run check` and `npm run test:extension` sequentially, since both build the same output directory. Offline demo persistence is proven; it does not prove Google synchronization.
- Chrome toolbar popups are capped at 800×600. Reclaim calendar space with compact controls rather than requesting a taller popup. FullCalendar v7's `slotMinHeight` cannot override content height: Forma time labels have default margins that must be reduced through `slotHeaderInnerClass` to fit an entire 24-hour week. Popup hourly slots preserve precise event times; month `dayMaxEvents: true` adapts overflow to available height, including reconnect banners.
- V0.2.1's `max-width: 100vw` / `max-height: 100dvh` component caps trapped the actual toolbar popup at its initial 25×25 minimum. Fixed dimensions on HTML in the head-linked popup stylesheet request native size before React; the body follows the granted viewport. Keep native `chrome.action.openPopup()`/`chrome.extension.getViews()` coverage: a regular page at a preset size missed this regression. Headless Chrome defaults to an 800×600 native display (only 498px below its toolbar); `--screen-info={1440x1000}` provides enough native room for an 800×600 popup independently of Playwright viewport emulation.
- Stage 3 uses an independent unexpanded IDs-only change feed and bounded server-expanded occurrence snapshots. Cursors cannot be mixed with timeMin/timeMax/orderBy/q. A change invalidates retained ranges; an unchanged feed updates validation timestamps without re-downloading instances. Recurrence/exception/DST expansion stays with Google (ADR 0004).
- Dexie schema 2 adds `ranges` and `syncStates` in place. Home cache defaults to 2 past/current/6 future months, plus one three-month browsing slot. Commit membership, orphan pruning, normalized events, and cursor together only after complete network results. Keep stale data on 410/failure; never mark partial data fresh. Startup recovers interrupted running flags.
- Stage 3 adds `calendar.events.readonly`; existing users may need to add it to OAuth Data Access and reconnect explicitly. No write scope or new client/server is needed. Live event-scope and two-account acceptance remain pending despite synthetic coverage.
- OAuth tokens are transient; provider sync cursors are local durable state. Cursor-free UI metadata and aggregate diagnostics must stay free of cursor values and account/calendar IDs. Event text renders as plain text and links allow HTTPS only.
- The stage 3 browser flow copies the production bundle to a temporary directory and replaces only that copy's public OAuth client with a synthetic one. Worker-level identity/fetch fixtures exercise real orchestration, Dexie and UI; never rewrite `.env.local` or the final build for fixtures. Google-cache survival through an offline full-browser restart is covered without claiming live Google verification.
- The Google adapter consumes response bodies. Tests that need multiple fetches must return a fresh Response per call; reusing a consumed Response can falsely turn a pagination-loop assertion into a transport error.
- The project's OAuth Data Access page was empty; the four app scopes were added through the existing Cloud Console session and Google's “Data access changes saved!” confirmation was observed on 2026-11-01. Actual user event consent/live sync remains pending. The local SDK still fails with OS-level “Operation not permitted” even with execution escalation. Do not confuse `gcloud iam oauth-clients` (Workforce Identity Federation) with the extension's standard OAuth client/consent configuration.
- At the user's explicit request, Cloud Data Access additionally predeclares `calendar.events` for future stage 4; saving was verified. This did not alter current runtime SCOPES/manifest or user grants. Add runtime write consent with the event-writing feature. Future desktop/audio permissions are Chrome `notifications`/`offscreen`; snooze/DND/local sounds/time zones need no additional Google scope.
- V0.3.0 manual sync filled the Google cache without changing the saved demo display source. V0.3.1 selects Google in the worker router before manual `SYNC_EVENTS`; automatic requests preserve demo choice, and failures keep Google/error/coverage visible. The Settings action says “Sync and show Google calendars.” Browser coverage checks the actual action updates an already open popup and full calendar, rather than manually toggling source first.

- V0.3.2 removes preview mode entirely: no data-source setting or sample commands/generator in production. Both surfaces read Google events only. Dexie schema 3 drops `demoEvents` and deletes only `demo-v1:` meta keys; preserve Google events/ranges/syncStates and unrelated metadata. Test-only fictional records live under `tests/fixtures/`. Old `dataSource` settings are stripped by schema parsing and cannot select a preview.
- The FullCalendar week current-time dot can extend past the visible day near midnight and create a tiny scrollbar. Use the public `dayLaneClass` hook with popup-only `overflow: clip`; `dayCellClass` does not style timed lanes. The popup test fixes its clock at 23:59 UTC to cover this boundary deterministically.
