# Durable notes for future agents

Keep concise, verified implementation facts here. Include the date and supporting source/test when it helps. Store no credentials, personal account information, raw API responses, or speculative findings. Move major design choices into an ADR.

## 2026-11-01

- This project began as an empty folder. The user requested local Git and documentation; no remote or publishing is authorized by that request.
- The unpacked extension ID is fixed by `config/extension-key.json`. `npm run extension:id` prints it. The public key can be committed; a private signing key must not be.
- The user configured an OAuth client in the ignored local environment file. Never overwrite it or replace it with a synthetic test value in a final build. Full real OAuth validation remains pending until the validation matrix is exercised.
- Account identity is Google's verified `sub`. Pin known-account token requests to it and compare returned identity before calendar access.
- Native account chooser behavior remains unverified with actual accounts. Do not infer success from injected adapter tests.
- Stage 1's timing preference schedules authentication/calendar-list checks, not event synchronization. Full custom notification sounds and event-sync settings remain in the plan.
- In restricted coding environments, npm registry access and launching Chromium may need sandbox escalation. The successful browser tests used a temporary profile and `PLAYWRIGHT_BROWSERS_PATH=/private/tmp/calendar-checker-browsers`; personal Chrome data was never used.
- Account toggle state is controlled by the persisted worker response. Browser tests should click and await the final checked state instead of assuming synchronous checkbox updates.
- WXT manifest environment values must be read in the manifest callback, after dotenv loading. See `wxt.config.ts` and WXT environment-variable documentation.
- Avoid shell variable names such as `path` in zsh: `path` is tied to `PATH` and can accidentally hide installed tooling. Use task-specific variable names.
- A generic connection error after consent was traced to calling stored native `fetch` as `this.fetcher(...)`. Chrome requires the Window/Worker global receiver and threw `Illegal invocation` before any request. Direct probes worked, while injected Node mocks missed this. The default transport now wraps `globalThis.fetch`; preserve this wrapper and its real-worker test.
- Transport diagnostics use fixed safe stages/categories plus HTTP status or a bounded native numeric code. Never retain full Chrome/provider error strings. GET retries are bounded to two attempts, and partial-body timeouts are transport failures rather than malformed JSON.
- After the native-fetch fix was rebuilt/reloaded, the user confirmed successful account connection on 2026-11-01. This verifies the first account flow; multi-account and lifecycle acceptance are still pending.
- Stage 2 uses FullCalendar v7's native React package, with daygrid/timegrid/interaction and Forma theme bundled. V6 examples and hashed internal CSS selectors are unsuitable. Use installed types and public class hooks/theme variables. Override theme variables on the calendar's `data-color-scheme` root for consistent dark mode.
- FullCalendar's day-cell event container uses measured inline `min-height` for its absolutely positioned events. Do not force that container to zero: overflow controls will overlap events. The compact popup instead reduces date/event text sizes and row minimum height through public hooks. The Chromium test verifies all six rows and overflow geometry.
- Historical stage 2: `calendar-checker-events` schema 1 separates `events`, `demoEvents`, and `meta`. Only worker commands write samples; reset clears sample rows and `demo-v1:` markers. Google sync has no writer yet. Superseded by schema 3 removal of preview data.
- Old stage 1 preferences receive additive appearance defaults. Commands use strict partial patches with per-key calendar visibility merging. Full preference objects must not enter diagnostics: visibility keys contain account/calendar IDs.
- Timed event ordering compares actual Temporal instants, including fractional seconds. All-day ends stay exclusive and date-only. The tests exercise Warsaw's March 2026 DST change and overnight date labels.
- Stage 2 passes 67 unit/adapter tests and three isolated Chromium tests. Run `npm run check` and `npm run test:extension` sequentially, since both build the same output directory. Offline demo persistence is proven; it does not prove Google synchronization.
- Chrome toolbar popups are capped at 800×600. Reclaim calendar space with compact controls rather than requesting a taller popup. FullCalendar v7's `slotMinHeight` cannot override content height: Forma time labels have default margins that must be reduced through `slotHeaderInnerClass` to fit an entire 24-hour week. Popup hourly slots preserve precise event times; month `dayMaxEvents: true` adapts overflow to available height, including reconnect banners.
- V0.2.1's `max-width: 100vw` / `max-height: 100dvh` component caps trapped the actual toolbar popup at its initial 25×25 minimum. Fixed dimensions on HTML in the head-linked popup stylesheet request native size before React; the body follows the granted viewport. Keep native `chrome.action.openPopup()`/`chrome.extension.getViews()` coverage: a regular page at a preset size missed this regression. Headless Chrome defaults to an 800×600 native display (only 498px below its toolbar); `--screen-info={1440x1000}` provides enough native room for an 800×600 popup independently of Playwright viewport emulation.
- Stage 3 uses an independent unexpanded IDs-only change feed and bounded server-expanded occurrence snapshots. Cursors cannot be mixed with timeMin/timeMax/orderBy/q. A change invalidates retained ranges; an unchanged feed updates validation timestamps without re-downloading instances. Recurrence/exception/DST expansion stays with Google (ADR 0004).
- Dexie schema 2 adds `ranges` and `syncStates` in place. Home cache defaults to 2 past/current/6 future months, plus one three-month browsing slot. Commit membership, orphan pruning, normalized events, and cursor together only after complete network results. Keep stale data on 410/failure; never mark partial data fresh. Startup recovers interrupted running flags.
- Stage 3 adds `calendar.events.readonly`; existing users may need to add it to OAuth Data Access and reconnect explicitly. No write scope or new client/server is needed. Live event-scope and two-account acceptance remain pending despite synthetic coverage.
- OAuth tokens are transient; provider sync cursors are local durable state. Cursor-free UI metadata and aggregate diagnostics must stay free of cursor values and account/calendar IDs. Event text renders as plain text and links allow HTTPS only.
- The stage 3 browser flow copies the production bundle to a temporary directory and replaces only that copy's public OAuth client with a synthetic one. Worker-level identity/fetch fixtures exercise real orchestration, Dexie and UI; never rewrite `.env.local` or the final build for fixtures. Google-cache survival through an offline full-browser restart is covered without claiming live Google verification.
- The Google adapter consumes response bodies. Tests that need multiple fetches must return a fresh Response per call; reusing a consumed Response can falsely turn a pagination-loop assertion into a transport error.
- The project's OAuth Data Access page was empty; the four app scopes were added through the existing Cloud Console session and Google's “Data access changes saved!” confirmation was observed on 2026-11-01. Actual user event consent/live sync remains pending. The local SDK still fails with OS-level “Operation not permitted” even with execution escalation. Do not confuse `gcloud iam oauth-clients` (Workforce Identity Federation) with the extension's standard OAuth client/consent configuration.
- At the user's explicit request, Cloud Data Access additionally predeclares `calendar.events` for future stage 4; saving was verified. This did not alter current runtime SCOPES/manifest or user grants. Add runtime write consent with the event-writing feature. Future desktop/audio permissions are Chrome `notifications`/`offscreen`; snooze/DND/local sounds/time zones need no additional Google scope.
- V0.3.0 manual sync filled the Google cache without changing the saved demo display source. V0.3.1 selects Google in the worker router before manual `SYNC_EVENTS`; automatic requests preserve demo choice, and failures keep Google/error/coverage visible. The Settings action says “Sync and show Google calendars.” Browser coverage checks the actual action updates an already open popup and full calendar, rather than manually toggling source first.

- V0.3.2 removes preview mode entirely: no data-source setting or sample commands/generator in production. Both surfaces read Google events only. Dexie schema 3 drops `demoEvents` and deletes only `demo-v1:` meta keys; preserve Google events/ranges/syncStates and unrelated metadata. Test-only fictional records live under `tests/fixtures/`. Old `dataSource` settings are stripped by schema parsing and cannot select a preview.
- The FullCalendar week current-time dot can extend past the visible day near midnight and create a tiny scrollbar. Use the public `dayLaneClass` hook with popup-only `overflow: clip`; `dayCellClass` does not style timed lanes. The popup test fixes its clock at 23:59 UTC to cover this boundary deterministically.

- V0.3.3: clearing native token state did not force Google's account chooser in the user's second-account attempt. Do not repeat that as a proven solution or revoke consent automatically. `web-identity.ts` offers a separately configured Web-client flow with exact Chrome redirect/state/scope validation. Existing accounts stay native; web accounts keep `authMethod: web`, never native-fallback. Tokens are worker-memory-only; silent renewal depends on Google session and is not a refresh-token guarantee. ADR 0005 records the documented legacy implicit-flow caveat. Duplicate Add is a failure before calendar reads, preserving all existing metadata. Public Web client defaults may come from ignored `WXT_GOOGLE_WEB_CLIENT_ID`; saved settings override them. Synthetic native tests explicitly disable that setting to avoid accidental live chooser windows.

- V0.3.4 week layout: readable/scroll is the default, with `weekHourHeight=48` (32–120 pixels). Map minimum hour height to public `slotMinHeight` according to slot duration; full calendar's half-hour slots get half the minimum. Fit is an explicit shared preference using hourly slots/compact labels and zero explicit minimum. Never restore unconditional popup compression or remove native document sizing. Tests must distinguish intentional internal week scrolling from unwanted page/horizontal overflow; fit/month checks remain scroll-free. Keep the saved minimum when fit mode is selected.
- Fit mode in the full calendar also needs the public `dayLaneClass` boundary clipping for the current-time marker; at 23:59 its dot can otherwise create a tiny scroll range. Week-layout browser checks fix both surfaces at 23:59 UTC when switching from scroll to fit.

- V0.3.5: toolbar event text is `HH:mm` for today's next timed start, or `+Nd` by local calendar-date difference for later dates. Do not divide milliseconds by 24 hours (DST); use the primary zone/Temporal dates. Exclude past starts, all-day/declined events, paused/hidden calendars, and prefer the UI's best-covered shared-calendar copy for each candidate day. Reconnect/storage warnings outrank event text. Only the tooltip includes event details, always labelled as saved data.
- Keep badge rendering centralized in `ChromeBadge`; AuthService saves and startup reconstruct it, and the existing one-minute sync alarm refreshes it even when no network work is due. Catch toolbar API failures around scheduler refreshes so they cannot block synchronization. Badge cache queries use a whole-second ISO lower bound plus actual timestamp comparison because normalized instants can omit fractional seconds.
- The icon generator draws a full-canvas calendar with transparent corners, no separate background tile, and local supersampling. Generate with `node scripts/generate-icons.mjs`; toolbar `action.default_icon` includes 16/24/32/48-pixel assets. Preserve the extension key/OAuth config when changing imagery.

- V0.3.6: event badge background comes from the selected normalized `event.color`, matching the calendar UI for time and +Nd labels. Choose black/white badge text using relative luminance and the higher contrast ratio, rather than forcing white on light calendar colors. Reconnect/storage warning badges remain red.

- V0.3.7: FullCalendar 7.1.3's MorePopover clamps horizontal position/top but not its bottom. Use public `popoverClass` and `dayCellClass`/`dayCellInnerClass` with `info.inPopover` for bounded dimensions, an independently scrolling body and a fixed header. A measured viewport correction watches owned panel classes and resize/reposition events; never target hashed library classes. Use `window.innerWidth/innerHeight`, not the popup document's requested HTML size. Keep `--fc-popover-z` below hover cards and modal details.
- Week auto-focus uses public `scrollToTime` after measured slot sizes settle. Scroll to slightly before the current hour only if the current time is outside the scrolling viewport, within the selected hour range and not in fit mode. Observe the slot's parent for sizing (the inner label can retain its height while the hour row grows). Do not include periodic clock state in effect dependencies, which would fight manual scrolling.

- Sidebar backdrops must follow the same CSS breakpoints as the drawer: always in the popup, and at widths up to 700px for the full calendar. Keep the backdrop below the drawer and above calendar controls, consuming the dismiss click without click-through. Leave it hidden for the persistent desktop sidebar.

## 2026-11-02 · stage 4

- Dexie schema 4 adds `outbox` and bounded `editBases` without altering Google event/range/cursor data. Outbox records own their original version and local preview. Snapshot replacement cannot delete unsent work; account removal checks pending count before metadata removal. Calendar reconciliation cleans detached master bases but preserves pending operations.
- Save commits locally before network work. HTTP write transport never blindly retries mutations. Stable UUID-derived IDs plus private `calendarCheckerMutation` markers acknowledge uncertain creations/edits; GET and If-Match prevent silent version overwrites. Acknowledged rows remain until a successful atomic snapshot commit, preserving the overlay during refresh failures.
- Whole-series edits load the original master and its ETag, original DTSTART and recurrence; never use an expanded selected instance as the master. Instance edits never patch recurrence. Default edits preserve complex rules and unrelated fields/guests/conference data by patching only changed fields. This-and-following splits and calendar moves are not implemented.
- Event editor all-day ends are inclusive in the form and exclusive in storage/API. Changed local times use Temporal with DST disambiguation rejection; untouched instants preserve their original offset/seconds. Keep editor actions outside the scrolling fieldset, inside a dedicated `.editor-scroll` div, with grid content inside the disabled fieldset. Use `overflow: clip` on the outer dialog/form so focus scrolling cannot move their header/footer.
- Runtime now includes `calendar.events` (the Cloud Data Access declaration alone never grants it). Existing native/Web accounts require scope consent through explicit Reconnect as needed. No additional Chrome permissions or token persistence are introduced.

- Keep bounded, content-free request receipts in `meta`, committed atomically with outbox insertion. A lost UI reply must not allow reusing an accepted ID for a changed form or recreate work already settled by read sync. Pending operations protect their receipts from pruning.

- V0.4.1: FullCalendar month cells classify clicks as all-day, but editor creation must default to one timed hour. Pass only the clicked start; initialize timed/default-zone dates separately and retain all-day mode only for an existing all-day event or an explicit checkbox. Move the end with the start without dropping untouched seconds. Use a nested Radix clock dialog with explicit trigger-focus restoration; keep time-zone selection separate from its empty-on-open search. Scroll the bounded zone panel and delete confirmation inside `.editor-scroll`, preserving fixed header/actions.

## 2026-11-02 · stage 5

- Schema 5 adds independent reminder/sound tables. Reminder identity omits account ID to deduplicate shared calendars; account enablement and reminder overrides apply, display visibility/search/type filters do not. The scheduler has its own SerialQueue so Google sync/interactive auth cannot block due alerts. Rebuild one-shot/watchdog alarms at startup and keep snoozes/delivery state durable.
- Persist sound attempts before audio, preserve desktop IDs across uncertain restarts, and never claim atomic exactly-once OS delivery. Multiple missed offsets coalesce; DND schedules use named-zone starting weekdays for overnight periods. Keep record cleanup bounded while retaining seven days of deduplication/history, and purge reminder content when its last account/calendar source is removed.
- Import validated local Blobs only; an offscreen AUDIO_PLAYBACK/BLOBS document decodes/plays them with bounded lifetimes. Only worker messages can control it. Serialize creation/playback/idle shutdown, revoke URLs, recover interrupted provisional imports, and distinguish explicit previews from automatic audio stopped by DND.
- Week dual-zone labels must evaluate each actual day, not use one current offset for the week. Public slotHeaderContent supplies the primary slot time; show distinct secondary conversions/date shifts across DST changes. Exact event previews/details use original instants, while all-day dates remain unchanged.
- Raw IndexedDB writes in browser fixtures do not broadcast Dexie mutations to an already-open useLiveQuery. Seed before opening a surface or reload it after fixture seeding. Production cache/outbox mutations remain worker-owned Dexie transactions.

## 2026-11-02 · busy-only availability

- Google `calendar.events` does not authorize freeBusy queries; v0.5.2 adds `calendar.events.freebusy` with explicit Reconnect. Keep bounded free/busy polling independent of event change cursors. A nested calendar error in an HTTP 200 response must not establish empty coverage.
- Availability keys are local UTC-day segments, not Google event IDs. Never edit them, generate event reminders/countdowns from them, or let a busy snapshot acknowledge pending event writes. Prefer detailed shared copies at equal coverage and rebuild snapshots when access mode changes. See ADR 0008.

- The availability scope was explicitly approved by the user and save-confirmed in the existing Cloud project on 2026-11-02. This does not prove an active account grant; reload/Reconnect and live busy-calendar verification remain pending.
